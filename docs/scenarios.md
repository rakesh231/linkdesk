# Three engineering scenarios

## 1. Greenfield: a usable shortening service

**Intent:** turn a long URL into a persistent shareable link. **Constraints:** Java/Spring, simple local setup, no external services. **Acceptance:** create → HEAD → GET → count → disable; invalid URL and duplicate alias return useful errors; state is durable across restarts.

**Decomposition:** URL/alias policy → H2 schema/repository → code generator and allocation → transactional lifecycle service → HTTP endpoints → tests. Dependencies are explicit: endpoints depend on the service, which depends on persistence and policy. Core API baseline is commit `02076be`.

**Execution:** created the new package `com.rakesh.linkdesk`, fresh JDBC schema, domain records and REST endpoints. Standard Maven Wrapper files were generated by Maven. **Validation:** baseline `verify` passed; lifecycle and policy tests established the working foundation before analytics enhancement.

## 2. Brownfield: add daily analytics without losing correctness

**Intent:** extend that working baseline with a daily chart and dashboard. **Impacted flow:** redirect controller → visit transaction → repository counter → new daily bucket. Read path: stats endpoint → UTC window and zero fill → dashboard chart.

**Decomposition:** additive daily table → transactional bucket update → stats DTO/API → UI → backward-compatible schema and concurrency tests. **Acceptance:** a successful GET increments both counts once; HEAD does not count; storage failure cannot commit only one counter; existing links survive the schema extension.

**Execution:** after the baseline commit, added `daily_visits`, zero-filled stats and the new dashboard. Reused the link-row lock to protect first-bucket insertion. Added fault injection, 40-way request workload, alias contention and disable/GET interleaving tests. **Validation:** forced a daily-write failure and observed 503 with both counters unchanged; preserved legacy links by applying the new schema twice in the compatibility test.

## 3. Ambiguity: what is a “click,” and what happens on expiration?

The requirement does not specify unique humans, bot filtering, time zones, HEAD probes or the exact expiry boundary. Chosen assumptions: each admitted GET counts; HEAD does not; UTC defines daily buckets; expiration at the exact instant is inactive; repeated disable succeeds; inactive names remain reserved. These are explicit product choices for review, not a claim of additional stakeholder approval.

**Decomposition:** define semantics → isolate the clock → implement lifecycle comparison and read-only HEAD → encode tests → explain the UI metric. **Validation:** fixed-clock boundary tests, lifecycle integration test, daily-stat HEAD exclusion and failed-redirect exclusion. UI labels total visits rather than unique visitors.

## Review checklist

- Read the architecture and API contract; confirm the assumptions fit the assessment.
- Run `./mvnw verify` and the live smoke script.
- Review the fresh implementation and AI log before submitting it as your work product.
- A successful automated run is not a substitute for human sign-off.
